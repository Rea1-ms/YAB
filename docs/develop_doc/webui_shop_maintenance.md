# 网页与商店维护

这里整理网页弹窗、应用图标和商店漏识别的排查方法，也说明当前配置保存后什么时候生效。说明以当前源码为准，配置热更新仍是暂缓方案。

## 输入框宽度

新建、重命名配置的弹窗共用 `webapp/src/lib/components/Modal.svelte`（弹窗组件）。输入框应占满弹窗内容区，保留左右内边距；同时检查弹窗最小宽度、窄屏最大宽度和输入框本身的宽度限制。

修改后分别打开宽屏和窄屏页面，确认输入框左右边界与内容区对齐、没有横向溢出。前端检查和构建通过，只能证明代码可以构建，布局仍需要看实际页面。

## 网页图标

浏览器标签和网页侧栏共用 `/favicon.ico`（网站图标），对应 `webapp/public/favicon.ico`（静态图标文件），素材来自 `assets/logo.ico`（应用图标）。标签引用在 `webapp/index.html`（网页入口），侧栏引用在 `webapp/src/App.svelte`（主界面）。更新品牌图标时，要一起检查这些位置。

`server/frontend.py`（网页准备入口）会比较源文件与构建首页的修改时间，检查范围包括 `webapp/public`（静态资源目录）。只更新图标也应触发重新构建，不能继续复用旧产物。完整发行包直接使用内置网页，需重新打包才能包含更新后的资源。

验证时检查图标请求成功、返回内容确实是图标，并观察标签与侧栏显示。桌面程序图标正常，不能代替网页图标的验证。

## 商店漏识别

商店选择逻辑在 `module/shop/shop_utils.py`（商店工具）。商品编号取决于行和固定列位置，不能按本次识别到了几件依次编号。例如，第六行第二列是第 22 件；漏掉第二列后，第三、四列仍是第 23、24 件。

维护时保留这些约束：

- 单点颜色检查漏掉某列后，在已识别行内用已有货币模板复查缺列；找不到模板就保留缺项，不能根据邻居猜测商品存在。
- 缺项时先重新截图，不推进当前行编号。滚动后的重叠行不能重复计数，末行列数按配置清单剩余长度确定，允许不足四件。
- 连续三次缺项或空识别、连续三次滑动无进展时，明确报错并停止购买。滑动后无法定位商品也直接报错；整个检查循环另有次数上限。
- 每件商品最多点击勾选三次，一组待选商品的确认总等待为 15 秒；识别和勾选过程都要响应停止请求。

离线回归在 `develop_tools/test/test_shop_selection.py`（商店回归），固定样本是 `develop_tools/test/fixtures/global_shop_last_row.png`（国际服商店末行截图）。它覆盖缺列补识别、编号不偏移、短暂漏检恢复、重叠行、末行不足四件、滑动停滞、勾选超时及停止请求。

在项目根目录运行已有回归，命令中的 `-B`（不生成字节码缓存）用于减少额外文件：

```powershell
uv run python -B -m unittest -q develop_tools.test.test_shop_selection develop_tools.test.test_tactical_shop_config develop_tools.test.test_webui_runtime.FrontendTests
```

截图回放和模拟缺项证明的是识别、编号及退出行为，不代表完成实机购买。若仍有漏检，应保留当时原始截图、服务器与语言、目标编号、识别行列和滑动日志，再核对模板与坐标。

## 配置何时生效

文件保存、网页显示和任务执行是三个不同环节，目前没有统一的目录监听与热更新机制。

| 环节 | 当前行为 |
|---|---|
| 配置读取 | `ConfigSet.get()`（单项读取）每次重新读取用户配置；直接访问已持有的配置对象不会因此自动刷新 |
| 配置写入 | `set()`（单项设置）先重读再修改并保存；`update()`（兼容更新入口）调用同一逻辑，也会保存文件 |
| 网页保存 | 服务保存后主动推送相应配置主题，页面据此更新；配置类本身不会自动同步界面 |
| 外部编辑 | 修改文件不会主动向已打开的网页推送；重新加载网页可以重取当前配置 |
| 运行任务 | 工作线程主要使用初始化时复制的配置，不能假定每项任务前都会重新读取普通参数 |
| 每日刷新 | 只处理每日计数与扫荡待办，不是通用配置重载 |
| 事件调度 | `event.json`（事件配置）在调度循环中重读，空闲等待时约每秒一次；不会中断当前任务，任务结束时仍会写回调度时间 |
| 初始化参数 | 设备、服务器、截图及控制方式等在初始化时使用；修改后停止该配置，等工作线程退出再启动 |
| 网页监听 | 地址和端口保存在全局网页配置中，重启服务后生效 |

普通任务参数需要确保生效时，也应停止该配置并重新启动。调度重读不等于运行配置全部热更新，外部编辑事件文件也不等于能立即影响正在执行的任务。

配置类的接口说明见 [ConfigSet（配置集合）](./script/ConfigSet.md)。

## 配置热更新（暂缓）

本次对照 [ALAS（碧蓝航线自动化脚本）](https://github.com/LmeSzinc/AzurLaneAutoScript) 的源码时，确认其等待阶段约每 5 秒比较配置文件修改时间，并在任务结束后清除配置缓存；这不是持续监听整个配置目录。以后对齐时仍需核对对应版本，不能只凭界面表现推断实现。

YAB（蔚蓝档案自动化脚本）目前只讨论了以下方向，尚未实现：

1. 约每秒检查配置目录与文件修改时间，检测增删和内容变更，推送网页；读取失败时保留原配置并重试，避免读取只写了一半的文件。
2. 普通参数在下一项任务开始前重新读取；等待中的调度及时更新，当前任务不因外部编辑被中断。
3. 设备、服务器等初始化参数提示停止并重新启动后生效，网页监听参数仍需重启服务。

重新开始这项工作时，先明确哪些参数可以在任务边界更新，再处理外部文件修改与网页保存的并发写入。
