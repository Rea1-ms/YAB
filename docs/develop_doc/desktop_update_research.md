# 桌面更新方案研究

建议先复用现有安装器，接入 electron-updater（桌面更新库），完成安装版的检查、下载和重启更新；整包更新跑通以后，再根据实际下载量决定是否拆分程序和资源。

本文依据 2026 年 11 月 13 日的本地源码和公开更新库源码整理。当天已按此方案接入安装版更新；下文保留研究时的取舍，实际操作与验证范围以 desktop/README.md（桌面说明）为准。尚未执行线上跨版本覆盖升级。

2026 年 11 月 14 日调整：程序改为直接从安装目录运行，取消本体副本、版本切换和自动回退。
依赖环境继续复用，配置位置保持原约定；以下关于旧版本隔离和后端回退的描述仅为当时的研究记录。

2026 年 11 月 15 日补充当前交互：正式安装版每次主界面启动完成后、进入“更新与帮助”时自动检查，状态及简短错误显示在检查按钮后。30 秒间隔只限制自动触发，手动检查可立即重试；正在检查、下载、等待安装或安装时不重复检查。仅检查版本，不自动下载或安装。

参照本机 MXU v2.10.0-beta.2（Maa 新界面版本）的启动与每日定时安排，增加可选的本地时分检查，默认关闭、默认时间 08:00。它不是每小时轮询，也不限制每天只能检查一次。开关和时间保存在安装目录内的 config/desktop-update.json（更新检查设置）；安装结果仍用安装目录根部的 desktop-update.json（更新状态记录），不创建每日检查日期文件。

## 现有基础够用到哪里

YAB（本项目）已经具备这些基础：

- 程序与依赖环境分开保存，依赖没有变化时可以复用环境；完整包离线准备，轻量包按锁定清单联网准备。
- 发行文件逐项校验，后端与识别服务就绪后记录当前版本；安装前不复制配置或安装包到用户数据目录。
- 安装器覆盖更新保留配置，并处理旧程序占用时的恢复。

接入前缺少在线查询、下载、安装协调及对应发布清单。当前桌面已有独立更新入口；普通浏览器中的旧启动器更新设置仍使用旧项目的仓库和镜像资源，不能直接当成新桌面版的更新入口。

现有回退也有明确范围：它恢复的是后端程序与环境，当前运行的桌面壳不会随之恢复。后端成功判断发生在主界面加载之前，不能把它当成整个桌面程序升级成功。

## 几个项目分别值得参考什么

| 参考项目 | 实际做法 | 对本项目的价值与限制 |
|---|---|---|
| StarRailCopilot（星铁助手）与 AutoEpicSeven（第七史诗助手） | 同步源码，再检查和安装依赖；等待任务结束后更新，支持内容分发加速与版本库方式回退 | 任务协调、下载重试和依赖检查值得借鉴。直接修改源码和环境，不能直接用于更新桌面壳，也不具备完整发行包的版本隔离 |
| Alasio（自动化框架） | 自有整包与差分格式，校验旧文件和新文件，先写临时文件，逐项替换，最后提交版本索引；独占锁防止同时更新，中断后继续修复 | 文件完整性和中断恢复做得细。需要同时维护包生成、索引、服务端和客户端，首版引入的维护量较大；逐文件原子替换也不等于整个目录同时切换 |
| zzz-od（绝区零一条龙） | 代码与运行环境分开，更新前检查兼容性；启动器在安装目录保留临时副本，替换失败恢复；下载源按顺序回退 | 最值得参考的是依赖兼容、文件占用重试和明确区分失败状态。其冻结运行环境与本项目独立解释器不同，不宜照搬安装流程 |
| M9A（重返未来助手）使用的 MXU（Maa 新界面） | 从镜像或官方发行页下载整包或变更包，直接处理安装目录并区分失败状态 | 渠道选择和文件替换值得参考，但压缩包覆盖与自建增量需要额外维护 |
| electron-updater（桌面更新库） | 下载已构建的安装包，校验摘要，支持安装包分块差分；差分不可用时下载整包，再交给安装器处理 | 与现有桌面壳和安装器最接近。任务停止、定制安装器兼容和启动后确认仍须由项目处理 |

本地的 M9A（重返未来助手）是发行目录，没有更新器源码；其界面声明确认使用 MXU（Maa 新界面），更新细节参考对应公开源码。其余项目直接检查了本地实现。

## 建议首版这样运行

用户看到的流程保持简单：检查更新 → 查看版本和说明 → 下载 → 重启并更新。

1. 下载期间继续使用当前版本。下载失败或取消不会影响正在运行的任务。
2. 点击安装即表示同意停止任务。阻止新任务启动和配置修改，请求停止现有任务，最多等待 30 秒；确认工作线程退出，再关闭后端及识别进程，执行安装。超时取消安装，不强杀仍在运行的任务。
3. 新版启动后，核对后端报告的版本、识别就绪状态和主界面加载结果。发生后端回退时明确显示，不能显示“更新成功”。

更新由桌面主进程执行，网页负责显示状态。普通浏览器保留原有页面；首版更新操作只开放给当前桌面窗口的受限接口。

electron-updater（桌面更新库）默认自动下载，并在普通退出时安装；当前实现已关闭这两个默认行为，由明确的下载和安装操作控制。现有退出处理会拦截退出、停止子进程后直接结束程序，接入时必须协调这一流程，验证安装器确实启动，且不会被文件占用或任务恢复流程干扰。

安装版先接入自动更新。解压版首版继续下载新版到独立目录，关闭旧程序后按现有方式迁移配置；不要未经验证就让解压版进入安装版更新流程。

## 发布和下载怎样少出问题

完整包、内置工具轻量包、系统工具轻量包分别使用独立更新清单。稳定版与测试版也分开，不能因文件名中包含变体就让三种包共用一个默认清单。

每次正式发行递增版本号。桌面版本、网页版本、后端版本和清单必须对应同一批构建，当前反复构建同一个 0.0.1 版本的方式只适合本地验证，不能用于正式更新判断。

当前通过 GitHub Release（平台发行页）分发，后续最多增加 Gitee Release（码云发行页）作为备用分发，尚未接入。先上传固定版本的安装包及分块清单，确认可下载后再发布最新版本清单。检查更新读取静态清单，避免每次都调用平台接口。

以后若增加码云发行分发，切换下载源时仍须保持目标版本、发行变体和摘要一致，不重新追踪另一个源的“最新版”。

保留 electron-updater（桌面更新库）的分块差分能力，并验证下载源支持范围请求、旧包与分块清单可用；失败时回退整包。它最终仍生成完整安装包，不需要项目自建补丁格式。实际节省量要用相邻两个正式版本测量，不能预先承诺。

实际发布步骤固定为：先同步 `pyproject.toml`（项目元信息）、`desktop/package.json`（桌面元信息）和
`webapp/package.json`（网页元信息）的版本号，运行 `uv lock`（更新 Python 锁文件），再执行 `uv sync --locked`、
两个前端/桌面依赖的 `pnpm install --frozen-lockfile`、网页检查和桌面回归。构建时在 Windows x64（64 位视窗系统）上依次运行：

```powershell
$env:YAB_RELEASE_NOTES = '本次更新说明'
pnpm -C desktop dist
pnpm -C desktop dist:lite
pnpm -C desktop dist:lite:system
```

每个变体都要上传安装包、对应的 `.exe.blockmap`（安装包分块清单）和 `latest*.yml`（更新清单），并放在同一个
`v<版本>`（版本标签）Release（平台发行）中。发布后用旧版本安装版实际完成一次检查、下载、重启和覆盖安装；
不能用源码运行、解压包或仅打开 GitHub 页面代替跨版本验证。

目前构建配置未启用发行签名，也未增加清单签名。摘要可以检查文件是否完整，但不能单独证明发布者身份。首版固定安全更新源，后续可配置可验证的发行签名；没有证书时也可增加公钥清单验证。镜像来源不能自行改变信任依据。

## 失败恢复要分别约定

| 发生的问题 | 首版应有的结果 |
|---|---|
| 检查失败、下载中断、摘要错误 | 保持当前版本可用，显示原因并允许重试 |
| 下载源不支持差分或旧包不可用 | 自动尝试同版本完整安装包 |
| 任务未停止、文件占用、安装被取消 | 不继续强行更新，保留配置、日志及恢复所需文件 |
| 新后端或新依赖环境启动失败 | 使用现有后端回退，显示回退结果，记录失败版本，避免反复自动尝试 |
| 桌面壳本身无法启动 | 需要用户重新下载对应版本安装包覆盖安装；当前不在用户数据目录保留旧安装包或配置副本 |

若后续要求桌面壳损坏也能自动恢复，需要一个不随主程序一起覆盖的外部启动器，负责保留旧版、启动候选版本并等待确认；超时再恢复旧版。这属于第二阶段，不能仅依靠现有后端回退或通用更新库承诺完成。

更新准备会在安装目录内、与 `YAB.exe`（桌面程序）同级写入一个很小的 `desktop-update.json`（更新状态记录），仅记录目标版本和完成状态，
不保存安装包或配置本体。项目不创建用户数据目录下的安装包或配置备份；electron-updater（桌面更新库）的临时缓存由更新库自行管理。

## 实施前需要验证的几件事

- 用两个不同版本的真实安装包验证检查、下载、安装、重启与版本一致；三种发行变体各自升级，不能交叉替换。
- 覆盖断网、错误摘要、差分失败、磁盘不足、安装取消及文件占用；检查失败后当前程序和配置仍可使用。
- 验证有任务时不会强行退出，等待更新时不会被调度重新启动任务；重启后沿用现有任务启动规则。
- 人为使新后端启动失败，核对后端失败提示；另测桌面壳无法启动时重新下载安装包覆盖安装。
- 单独验证定制安装器收到更新参数后的路径、数据保留、静默运行、权限和重新启动行为。现有普通安装回归不能替代这些检查。

建议第一批只完成安装版整包更新、三种变体分流、任务协调和失败恢复验证。自建差分、资源独立发布和桌面壳自动回退留到有实际需求时再做。
